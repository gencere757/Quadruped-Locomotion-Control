=== File header / fork rationale ===
# champgait_wave.py - fork of champgait.py (v6.11), Arda's "continuous CoM sway" idea.
#
# Forked on purpose instead of editing champgait.py directly, so if this experiment doesn't work out
# it can't break the working discrete CoM-centering controller over there.
#
# What's different: champgait.py's v6 rewrite runs the gait as a discrete state machine per leg -
# shift_com_to (converge), wait_for_safe_lift, do_swing, wait_for_settle - one leg at a time. Every
# failure this session had traced back to the same pattern: a SHIFT phase that moves the CoM some
# real distance, then a hard cut into SWING. The cycle-2 failures (FL slipping hard, 3x under
# different tuning) always hit during a bigger-than-usual shift right at that discrete transition -
# matches Arda's theory that stop/shift/restart creates real transients (yaw/pitch kicks, momentum
# built up and killed every step) that a smooth motion wouldn't.
#
# The fix: never let the lateral CoM position stop moving. Make it a continuous function of gait
# phase, y_com(t) = A*sin(omega*t), layered on top of the forward walking motion that was already
# continuous (each leg's own fore-aft stance sweep - this part predates champgait.py's discrete
# rewrite, see champ_old.py, the ancestor of the phase-clock code below). Since the sway is a smooth
# sine tied to the same phase clock that sequences the leg swings, weight starts shifting onto the
# next support tripod WHILE the current leg is still swinging, instead of "swing, stop, then figure
# out the next shift" - so there's no sudden discrete moment for a pivot/slip to happen at.
#
# champ_old.py already had this continuous phase clock (leg_phase_fracs/current_swing_leg/
# foot_offset_for_leg below are lightly adapted from it) but its only weight-shift trick was a crude
# fixed fore-aft bias (SHIFT_MAG_FRONT/BACK) on the other three legs during a swing - no real lateral
# shift at all, probably why it eventually needed the discrete CoM-centering rewrite in the first
# place (nothing was actually pushing the CoM to the right side of the support polygon). This fork
# keeps champgait.py's real fix for that - the 3-DOF leg_ik_3d (ABAD-driven lateral shift) plus its
# reach-aware max_safe_fy/clamp_fy - and drives the same body_shift[1] (fy) continuously off the sine
# instead of a converge-and-stop shift_com_to loop.
#
# Everything not about gait generation - leg_ik/leg_ik_3d/rotate, IMU + ground-truth telemetry,
# support-polygon/ZMP/capture-point math, pitch/roll/yaw correction, the safety-abort watchdog - is
# carried over unchanged from champgait.py (v6.11). Only the stuff between the "CONTINUOUS GAIT"
# markers below is new.

=== GAIT_PERIOD ===
# v3 fix - was 6.0 (champ_old.py's walking pace). At 6.0 the sway's own peak
# rate of change is 0.06*2pi/3.0 = 0.126 m/s, 3.35x faster than champgait.py's
# proven-safe CoM-shift rate (SHIFT_STEP_MAX/CONTROL_DT = 0.00075/0.02 =
# 0.0375 m/s - itself already tuned down twice to stop slipping, see SHIFT_KP's
# v6.8 comment). The v2 fix (peak lean at swing onset instead of mid-swing)
# still fell the same way, which rules out timing and points at rate: a
# 9.78 m/s^2 lateral accel spike showed up during ease-in with all 4 feet
# still planted and no swing happening - so the shift itself was just too fast,
# not badly timed. 24.0 gets the sway's peak rate down to 0.0314 m/s (computed
# below), safely under the 0.0375 cap. Makes the walk ~4x slower than
# champ_old.py's pace - that's the real cost of moving this much CoM weight
# without slipping. MAX_SHIFT_RATE below is a hard backstop regardless.

=== SWING_DUTY ===
# % of GAIT_PERIOD one leg spends swinging - same as champ_old.py. 4*0.15=0.6,
# not 1.0, so 40% of the cycle has all four feet down at once - more margin
# than a duty factor that keeps a leg always in the air.

=== CoM lateral sway design rationale (before SWAY_AMPLITUDE) ===
# Arda's continuous lateral CoM sway: y_com(t) = A*sin(omega*t)
# GAIT_ORDER=[BR,FL,FR,BL] alternates right/left/right/left, so the CoM only needs to lean fully to
# one side and back twice per GAIT_PERIOD (not four times) - once for the BR/FR pair, once for the
# FL/BL pair. So the sway's period is GAIT_PERIOD/2, not the full GAIT_PERIOD.
#
# Sign convention: OY is +1=left/-1=right, and this file's fy convention (from champgait.py's
# shift_com_to sign fix) is that increasing fy pushes the body toward -y (right), since a planted
# foot is fixed and a bigger foot-target offset moves the body the opposite way. Together that means:
# push the CoM toward negative fy (right) while a right leg (BR, FR) is swinging, so the other three
# legs (now further left) can support it - and toward positive fy (left) while a left leg (FL, BL)
# is swinging.
#
# v2 fix - used to peak at mid-swing (global_phase = LEG_PHASE_OFFSET[leg] + SWING_DUTY/2). That
# meant the lean was only cos(54deg) = 59% of full amplitude at the exact moment a leg lifts off
# (swing onset), so the robot started each swing on a still-transitioning, under-leaned CoM instead
# of an already-settled one. Confirmed in a failing run's log: gait engaged at fy=-0.0353
# (= -0.06*0.588) and started diverging (pitch/yaw/x-slip) the instant BR left the ground, before the
# lean had even finished. Fix: zero the phase offset so the peak lands at swing onset instead of
# mid-swing - body is already fully leaned when a leg lifts, and just relaxes back toward center/the
# other lean during the swing instead of still fighting to get there:
#     y_com(phase) = -SWAY_AMPLITUDE * cos(2*pi * phase / 0.5)
# Check: BR onset (phase=0): cos(0)=1 -> -A, full right lean, already there. FL onset (0.25):
# cos(pi)=-1 -> +A, full left lean. FR onset (0.5): cos(2pi)=1 -> -A. BL onset (0.75): cos(3pi)=-1 ->
# +A. All four line up on their own swing onsets for free, since SWING_DUTY's legs are spaced by
# exactly half the sway period (0.25 vs 0.5).

=== y_com_target v7 fix ===
# v7 fix: swapped the continuous cosine above for a piecewise hold-during-swing /
# transition-during-quad-stance shape, mirroring x_com_target's already-proven structure below.
# Found via actual CoM/ZMP/capture-point telemetry: the cosine's period is locked to SWING_DUTY so
# its peak does land at swing onset, but that says nothing about how long it stays near the peak.
# SWING_DUTY=0.15 is wider than the cosine's quarter-period (0.125), so on every swing the sway is
# already past its peak and swinging back through zero before that leg's swing even ends - usually
# recovers in time, but not always. On BL (last in GAIT_ORDER, phase [0.75,0.90)) one run's telemetry
# showed the ZMP margin going outside partway through BL's swing, capture point following right
# after, right as fy crossed zero and kept going - the CoM was leaning back toward BL's now-unsupported
# side before BL's foot was even down. Pitch grew unrecovered into a SAFETY ABORT ~3s later.
# x_com_target already solves this for the fore-aft axis by holding a constant lean for a leg's whole
# swing and only transitioning during quad-stance - do the same here instead of a sinusoid that's
# phase-aligned but not duration-matched.

=== x_com_target v4/v4.1 fix (fore-aft lean, before X_LEAN_AMPLITUDE) ===
# v4 fix: fore-aft (x) CoM lean - the piece the "tips backwards" reports were pointing at. champgait.py's
# discrete controller shifts to the centroid of the other three feet's actual world positions before
# every lift, both x and y. This file only ever built the y half (left/right sway) and left
# body_shift[0] (fx) at 0.0 the whole run. GAIT_ORDER=[BR,FL,FR,BL] is back,front,front,back, not
# alternating, so unlike the sway (which gets free half-period symmetry from R/L alternating) the back
# legs (BR, BL) are grouped together (onsets at phase 0 and 0.75, adjacent across the 1.0/0 wrap) and
# front legs (FL, FR) are grouped together (onsets at 0.25 and 0.5) - a real two-state thing, not a sine.
#
# v4.1 sign fix: first version had the sign backwards. Using CMD_HIP_OFFSET's hip geometry
# ((+-0.15, +-0.213)) plus each stance leg's foot_offset_for_leg(t) fx, the real centroid of the
# remaining 3 feet at BR's onset works out to cx=+0.058 (forward, as expected since BR is a back leg).
# But the same planted-foot-fixed rule already used for fy (a bigger commanded offset moves the body
# the opposite way, since the foot is fixed by friction) applies to fx too: the right command to reach
# that +0.058 centroid is fx=-0.058, not +0.058. The original code returned positive X at BR's onset -
# exactly backwards - confirmed on the recording: the body slid left AND back, when BR lifting should
# have needed left AND forward (left was already right from the y half; back-instead-of-forward is
# exactly what a flipped fx sign gives you). Fixed by negating both branches and recalibrating the
# magnitude from the real per-onset values (0.042-0.058 across the four onsets, not perfectly
# symmetric since STEP_LENGTH_FRONT != STEP_LENGTH_BACK) instead of the original half-guessed 0.03.

=== X_LEAN_AMPLITUDE ===
# v6: 0.05 matched the static centroid shift, but pitch kept climbing through
# both ease-in and the swing itself (not just a spike at swing onset), and
# doubling the ease duration (2.0s->4.0s) didn't help - if anything pitch at
# engagement got slightly worse. So it's not "ease ramp too fast", it's a
# sustained pitch bias from holding this fx lean for the whole swing window,
# which is ~3.6s at GAIT_PERIOD=24.0 - much longer than champgait.py's discrete
# controller ever held a single shift. Trading some static margin (was
# +0.058-0.085, still comfortably positive at 0.035) for less sustained torque.

=== LEG_LR / YAW_RATE_DAMPING v9 fix ===
# +1/-1 per leg, mirrors yaw correction left vs right
# v9: v7's mistake was doubling YAW_FX_GAIN, YAW_RATE_DAMPING, and MAX_YAW_FX all at once, so there
# was no way to tell which one caused the regression (2 falls, yaw got WORSE - +30.2deg net turn vs
# v8's +9.9 to +22.5deg range over 4 clean runs). Logs pointed at the D-term specifically:
# yaw_d = YAW_RATE_DAMPING * gyro_yaw_rate produced nonzero fx_term even with zero actual yaw error
# (err=+0.00deg during ease-in, but fx_term still moved from raw gyro noise) - it's reacting to sensor
# jitter, not real drift, and amplifying that just injects noise into the pitch balance.
# v9 isolates the two terms: disable the noisy D-term entirely (0.0), and give the P-term (a real,
# validated error signal) a modest 1.5x bump (not 2x) to make up for the correction only running during
# the shorter non-swing part of the now much-longer GAIT_PERIOD=24 cycle. MAX_YAW_FX raised to match so
# the clamp doesn't cap the bumped gain. Smaller, single-variable change on purpose, to avoid repeating
# v7's mistake - watch the next few runs for yaw drift actually dropping and no new pitch/roll wobble.

=== YAW_FEEDFORWARD_BIAS / YAW_FX_GAIN v17 fix ===
# constant nudge added to yaw correction
# v17 fix: v16 (scaling down the pitch gains for the confirmed 5.3x stiffer joints) worked - theta
# stayed under ~1 deg through 60+ seconds and 2+ full cycles on a run that previously would've aborted
# in cycle 1 - but that just exposed the next problem: yaw_err climbed continuously the whole time,

# isn't a correction hitting its ceiling, it's just too weak - the P-term has headroom left but can't

# authority, and raise MAX_YAW_FX to match (0.0375->0.075) so the clamp doesn't cap the doubled gain
# at the large errors this run already hit - same "raise the gain, raise the headroom to match" move
# v9 used to fix v7's regression. YAW_RATE_DAMPING stays 0.0 (still noisy per v9), YAW_FEEDFORWARD_BIAS
# untouched - only the P-term moves. Watch for yaw actually leveling off/reversing instead of climbing
# past 28 deg, and no new instability from the bigger correction.

=== control_loop yaw v11 fix (per-leg blackout) ===
# this leg's target foot position
# v11: yaw correction used to get zeroed for every leg whenever any leg was mid-swing (same
# protection champgait.py uses) - which blacked it out for most of the cycle at
# GAIT_PERIOD=24 (each swing ~3.6s), the real reason it could only ever partly cancel the
# drift. That blackout exists to protect the 3 stance legs - pushing planted feet
# asymmetrically while only 3 are grounded can tip an already-reduced support base. But that
# doesn't apply to the leg that's itself swinging - nothing planted there, so nudging its
# target doesn't move the body, just steers where that foot lands (real legged robots
# correct heading this way a lot). So now: the swinging leg gets full correction (steering
# via its own footfall), the other stance legs still get zero while someone else swings, and
# all four get it during quad-stance - correction runs in parallel with the gait far more of
# the time instead of only in the brief gaps between swings.

=== Crouch settle wait v14 fix ===
# v14 fix: this used to be a fixed 20*0.1s=2.0s wait regardless of whether the body had actually
# stopped bouncing from the crouch - the one handoff in this file not gated on measured stillness
# (every other one - ease_into_gait's cold start, ease_out_of_gait, the final tail - already is).
# Evidence: a run whose crouch settle was still oscillating (pitch -6.88..+5.02deg, speed_xy up to
# 0.30 m/s) right up to the fixed 2.0s cutoff fed that leftover energy into ease_into_gait, which
# resonated into a growing oscillation (pitch swinging +-20deg through the ramp instead of damping

# wait on actual measured stillness (speed and pitch/roll, not just speed) instead of a clock, with a
# capped max wait so a run that never quite settles can't hang forever.

=== End-of-run wait note ===
