                              # retuning, smooth the derivative more (lower this) before raising D again -
                              # don't just throw a bigger D at a noisy signal. Confirmed with real data: a
                              # fall during plain forward walking (roll correction off, so roll's not the

                              # (10 ticks) - enough to reject noise without being too slow to catch a real

                              # Watch the next runs for: does this calm pitch_rate/theta_d without bringing

                              # sustained-walk falls keep happening, try PITCH_RATE_DAMPING or

=== TROT_PERIOD ===
# was 1.6. Stride amplitude A = 0.5*vx*STANCE_DUTY*TROT_PERIOD in
                            # foot_target_for_leg scales directly with this, so a shorter period means
                            # shorter, more frequent strides at the same vx instead of big lunging ones -
                            # less mass swinging per step. Worth trying because the recurring falls at
                            # every p_gain/d_gain we tried (72.6 through 265) were almost always plain
                            # forward/back walking with turn=0, not a turn or joint-gain problem (that
                            # axis had plateaued). The legs got much heavier in the latest CAD export
                            # (thigh+shank mass roughly tripled), so each stride swings a lot more mass
                            # now, and the pitch-balance correction below (CORRECTION_FRACTION etc.) was
                            # tuned for the old lighter legs and never revisited - shrinking the
                            # disturbance itself felt safer to try first than retuning that loop blind.

=== STANCE_DUTY ===
# ported fix, was 0.5. At 0.5 the two pairs swing back-to-back with zero double-support
                   # overlap - the instant one pair lands the other lifts, so the body's only ever on 2
                   # legs, never 4. trot_demo.py root-caused its "huge periodic dips" to exactly this:
                   # support narrows to 2 diagonal legs every half-cycle, every cycle, not occasionally.
                   # Raising to 0.6 gives a real double-support window and cuts each leg's swing time by
                   # 20% (SWING_DUTY = 1 - STANCE_DUTY, 0.5 -> 0.4). In trot_demo.py this fixed yaw
                   # stability and raised average speed/distance. Two things to watch: (1) stride
                   # amplitude A = 0.5*abs(vx)*STANCE_DUTY*TROT_PERIOD scales with STANCE_DUTY too, so
                   # stride length also grows ~20% at the same vx - if turning gets less stable after
                   # this, that's probably why; (2) by itself this did NOT shrink trot_demo.py's dip
                   # amplitude (if anything slightly worse) - it took the feedforward pitch bias below on
                   # top of it to actually fix that. Don't expect this alone to fix the dips here either.

                            # (the yaw-hold fix, now reverted - see YAW_HOLD_KP), so not the moment to
                            # also stack a big speed bump on the already-fragile backward-walking case.

                            # the remaining failures are a stride disturbance still a bit too big for this
                            # heavier model, not a control-loop bug (the PITCH_RATE_DAMPING experiment
                            # already showed retuning that loop blind makes it worse). Same lever as
                            # TROT_PERIOD (stride amplitude A = 0.5*vx*STANCE_DUTY*TROT_PERIOD scales with
                            # vx too), just on the ceiling instead of the period - a 25% cut in top speed
                            # for real margin under the abort line. Watching the next runs (forward and
                            # backward) for new aborts before raising this further.

=== MAX_TURN ===
# steering intensity, -1.0 (full left) to +1.0 (full right) - not a
                            # calibrated rad/s. There's no measured-yaw-rate feedback in this file, so
                            # it's open-loop: the code never checks whether it actually achieved the turn

=== TURN_VX_GAIN ===
# Converts steering intensity into a per-side forward-speed offset - see
                             # foot_target_for_leg/control_loop. At full steering (+-1.0) each side's
                             # leg_vx shifts by +-TURN_VX_GAIN, so a full turn with target_vx==0 drives
                             # one side's legs forward and the other's backward - real differential-drive
                             # rotation in place, since foot_target_for_leg gets its amplitude and
                             # direction from this per-leg speed, not a bolted-on touchdown offset.
                             #
                             # History: started at MAX_VX, halved to 0.5*MAX_VX after run_log_turn_test.txt
                             # showed rotation working but pitch escalating cycle-over-cycle during
                             # full-strength turning (roll stayed bounded, ruling out roll/stance-narrowing -
                             # it's the turn disturbance overpowering the pitch correction). That made pure
                             # rotation and translate-only phases clean on the heavier model, after retuning
                             # p_gain/d_gain up through 72.6->145->217->250->265 (282 overshot). But across
                             # many runs at all those gains, "combined" (full vx AND full turn together) kept
                             # failing - same overpowering mechanism, just needing translation+turn stacked
                             # to trigger it. Cut to 0.35*MAX_VX, then with TROT_PERIOD=1.0 forward walk,
                             # rotation, and back walk all cleared cleanly (max pitch ~18deg, well under
                             # FLIP_LIMIT_DEG) - TROT_PERIOD turned out to be the real fix for plain-walking
                             # falls. Combined linear+angular was still the only failing phase, and fails
                             # fast: run_log_turn_test.txt showed pitch swinging -10 -> +14 -> -14deg within
                             # ~1.8s of combined starting, then aborting at -26.5deg - an oscillation, not a
                             # slow drift, so the stacked disturbance is still too strong for the pitch loop
                             # to damp before it resonates. Cut further to 0.2*MAX_VX. If combined still
                             # fails at this value, the next lever should be CORRECTION_FRACTION/
                             # PITCH_RATE_DAMPING (untouched since the old lighter-leg model), not cutting
                             # this further - below 0.2 it'd barely rotate at all while walking, which stops
                             # being a fix and starts being "don't turn while moving."

                            # gain used only for pure in-place turning (target_vx ~0), leaving TURN_VX_GAIN
                            # itself alone for whenever there's also forward/back motion. 0.4*MAX_VX doubles
                            # pure-turn authority - a first step, not final; watching the next test for
                            # usable rotation speed without new pitch/roll excursions before raising further.
                            #

                            # still reports "takes too long" AND "stalls in place at certain moments".

                            # then ~22deg across samples 481-521 (40 samples) - the per-sample rate swings
                            # ~8x between slow and fast patches, not a smooth constant creep. Consistent with

                            # can't overcome static ground friction until posture (pitch/roll, actively

                            # distribution. More authority won't necessarily kill every stall if that's
                            # right, but it directly attacks the "not enough torque" half of it, and there's
                            # a known-safe ceiling to use instead of guessing: TURN_VX_GAIN's own history
                            # says full-strength pure rotation caused pitch escalation, but 0.5*MAX_VX got
                            # "pure rotation and translate-only phases reliably clean" - only the combined
                            # case needed cutting further after that. Going to that already-validated
                            # 0.5*MAX_VX ceiling (up from 0.4), not higher. If stalling persists even at this
                            # safe max, that's the signal it's not a pure gain problem anymore, and the next
                            # lever should be something else (MAX_TURN_ACCEL, joint gains, the friction/
                            # contact model) rather than pushing past a ceiling this file's own history
                            # already flagged as unsafe.
                            #
                            # v3 (reverted partway, was 0.5*MAX_VX): confirmed - stalling persisted at 0.5x,
                            # exactly as flagged. But the log showed this isn't simple friction stiction: the
                            # stall windows line up with real physical stumbles - one stretch had pitch surge
                            # +1.8 -> +7.5deg AND body_xyz.x slide ~0.06m within a handful of samples, with
                            # yaw briefly reversing before resuming. That's a real destabilization event, not
                            # "not enough torque". Since 0.5*MAX_VX is a bigger disturbance than 0.4 was, and
                            # this file's whole turn-tuning history is built on "less disturbance = more
                            # stable" (why TURN_VX_GAIN itself got cut three times), backing off partway to
                            # 0.4*MAX_VX while also gating the forward-walking-shaped feedforward pitch bias
                            # out of pure rotation (see theta_ff's comment in control_loop - that bias was
                            # only ever validated for a fore-aft disturbance, not a torsional one, and may
                            # have just been adding noise). Testing both changes together since they're not
                            # competing hypotheses - less raw disturbance and removing a mismatched extra
                            # correction. Watching the next turn-in-place run for whether the stumbles
                            # specifically go away (not just average speed) before deciding whether either
                            # half actually mattered.

=== PITCH_RATE_DAMPING ===
# ported fix, was 0.15 (see the reverted history right below, kept for
                           # context - that's about 0.15 vs 0.3, not this new value, and its lesson still
                           # holds: don't jump back to 0.3 or higher). trot_demo.py hit the same periodic-
                           # dip complaint this file's users reported, and root-caused it as a theta_d/
                           # theta_p IMBALANCE, not a raw magnitude problem: with the old gain, theta_d
                           # was regularly 3-30x the size of theta_p sample-to-sample, meaning "pitch
                           # correction" was really just chasing pitch_rate noise instead of leaning
                           # against the actual pitch angle. Halving to 0.075 (with IDLE_PITCH_RATE_DAMPING
                           # halved to match below) brought the two terms back to roughly 1:1 in
                           # trot_demo.py's validation runs. On its own this did NOT shrink the dip
                           # amplitude there - it took a gait-timing change (STANCE_DUTY) and a
                           # feedforward term (both below) to actually do that - but it's a real fix to a
                           # real imbalance and worth carrying over regardless.
                           # Reverted attempt: briefly tried 0.3 (doubled) to fix an underdamped-looking
                           # oscillation, but it made things clearly worse - 3 straight runs failed
                           # immediately in forward walk, including one violent one (pitch +8.4 -> +5.0 ->
                           # abort at 26.1deg, with roll suddenly at 10.6deg and avg_yaw_rate=45.7deg/s - a
                           # fast tip/spin, not a slow climb) within under a second of the gait starting.
                           # latest_pitch_rate is a finite-difference derivative of a noisy signal, only
                           # lightly smoothed (PITCH_RATE_LPF_ALPHA=0.2 at the time), so doubling its gain
                           # likely amplified noise into real torque right at the crouch-to-gait transition
                           # (when pitch is changing fastest and least predictably) instead of adding clean
                           # damping - classic derivative kick. Back to 0.15 (now superseded by 0.075
                           # above). If this loop needs retuning again, smooth the derivative more first
                           # (lower PITCH_RATE_LPF_ALPHA) so it's trustworthy before raising the gain -
                           # don't just throw a bigger D at the same noisy signal.

=== IDLE_CORRECTION_FRACTION ===
# ported fix. trot_demo.py hit this same problem: a reactive pitch
                           # correction tuned for active walking, left running unconditionally even while
                           # idle/at rest, turned into an unstable clamp-saturating oscillator once there
                           # was nothing real left to correct - the live joint gains (p_gain=265/
                           # d_gain=10.6) are about 5.3x stiffer than what CORRECTION_FRACTION/
                           # PITCH_RATE_DAMPING above were tuned for (p_gain=50/d_gain=2). The fix there
                           # wasn't a blanket gain cut (that broke active-walking stability) but a
                           # phase-gated split: full gains while actually moving, this weaker 1/5.3-scaled
                           # pair otherwise - see IDLE_CORRECTION_FRACTION in trot_demo.py for the full
                           # reasoning (6-7 clean runs there, flat idle pitch/roll, no ringing). Porting it
                           # here because this file's own history describes the same failure under a
                           # different name: MAX_CORRECTION_RAD's comment shows pitch flipping sign and
                           # climbing steadily right after release ("release -> destabilizes -> falls"),
                           # speed_xy climbing instead of decaying - same overshoot mechanism, just
                           # triggered by key-release instead of "trot complete". Gated on is_moving below
                           # (this file's existing "released" signal) instead of adding a new flag.

=== IDLE_PITCH_RATE_DAMPING ===
# ported fix, was 0.028 (=0.15/5.3). Now 0.075/5.3 - keeps the same
                           # idle/active ratio now that PITCH_RATE_DAMPING was halved above, so the two
                           # stay proportional.

=== FEEDFORWARD_PITCH_BIAS_RAD ===
# ported fix, new mechanism not just a retuned gain.
                           # After PITCH_RATE_DAMPING and STANCE_DUTY were ported above and neither alone
                           # shrank trot_demo.py's per-swing dip, it added a different kind of
                           # correction - anticipatory instead of reactive. The gains above only respond
                           # after pitch/pitch_rate have already moved; this adds a small nose-up bias
                           # timed to when a leg pair is swinging (known ahead of time from the gait
                           # clock, not measured) - a half-sine that's zero at liftoff/touchdown and peaks
                           # mid-swing, exactly when support narrows to 2 diagonal legs and the body's
                           # most likely to pitch down. 5deg is deliberately conservative (roughly half
                           # the typical dip depth seen in trot_demo.py's logs) since this is open-loop
                           # and always-on rather than measured/gated. In trot_demo.py this brought dip
                           # amplitude back down to the original pre-fix baseline while keeping
                           # STANCE_DUTY's yaw/speed gains - this term, not the two gain changes above, is
                           # what actually shrinks the dip. See theta_ff in control_loop() below.

                            # The 0.3 run (flat, unmirrored roll_term applied the same to all 4 legs)
                            # showed backward jolts and near-loss-of-balance "lifting" during plain
                            # straight forward walking, lining up with roll_term spikes - so a

                            # to losing balance" symptom. The log shows pitch jumping sharply (e.g.
                            # +0.9->+11.3deg, +5.5->+12.6deg, +6.4->+18.5deg) right after the largest

                            # correction should do. Likely reason: PAIR_A/PAIR_B each combine one LEFT and

                            # correction pushes opposite signs onto the two legs currently bearing the

                            # shifting stance width - a plausible way to inject a pitch disturbance from
                            # what was meant to be a pure roll fix, worse than the original flat version's

=== YAW_HOLD_KP_INTRO ===
# yaw hold while walking/idle but not actively steering
# User report: "while walking backward, the yaw angle goes crazy". Checked run_log_manual.txt before
# touching anything: this file has ZERO yaw correction of any kind - TURN_VX_GAIN's comment already
# notes there's no measured-yaw-rate feedback here, but that was about steering accuracy, not drift
# while turn_target sits at 0.00 the whole time. A straight backward run (S held, A/D never touched,
# turn_target=0 for all 394 samples) drifted yaw from 0 to -57.4deg with nothing resisting it. The same
# straight FORWARD run (W held, same sample count, turn_target=0 throughout) stayed within roughly
# +/-10deg over the same span - so this is a real, backward-specific drift, not a display glitch or a
# wraparound bug (a -72.9deg reading elsewhere in the log was a deliberate full in-place turn, which is
# supposed to yaw a lot - that's steering working, not this problem, and isn't part of this comparison).
# Why it's specifically backward isn't pinned down yet - could be a real geometric/CG asymmetry, could
# be how foot_target_for_leg's direction-flip for vx<0 interacts with the diagonal trot pairs - but
# either way, there's currently nothing here to correct heading drift the way trot_demo.py does (its
# YAW_FX_GAIN/MAX_YAW_FX/yaw_integral).
#
# Can't just copy trot_demo.py's version as-is: that file only ever walks in a straight line (one fixed
# heading baseline for the whole run), while this file's whole point is deliberate A/D steering -
# correcting against one fixed heading would fight the user's own turns. Instead: only correct while
# NOT actively turning (is_turning, same MOVE_EPS_TURN deadband already used for "released"), and lock
# in a fresh target heading the moment turning stops rather than one baseline for the whole session -
# so a turn-then-walk-straight sequence gets held to the heading it ended up at after the turn, not
# dragged back to wherever it started. Only applied to the currently-swinging pair's legs (via LEG_LR),
# same reasoning as trot_demo.py's yaw fix: pushing a planted stance leg's fx couples into pitch, but an
# airborne swing leg's landing spot doesn't. Starting from trot_demo.py's own pre-v1/v2 gains
# (YAW_FX_GAIN=0.15, MAX_YAW_FX=0.06) since those are already validated there as stable and
# non-oscillating, rather than guessing new numbers.

=== TROT_PHASE_CLOCK_NOTE ===
# The trot phase clock only advances while there's live input above a small deadband; otherwise all
# four feet hold a static stance and the phase resets to 0, so movement always resumes from a clean

=== FOOT_RATE_LIMIT_INTRO ===
# Foot targets go straight to IK every tick with no smoothing of their own (the trot waveform is smooth
# by construction, but switching between "trotting" and "static stance" above is a mode change, not a
# continuous function) - rate-limit them here so that switch is a quick glide, not an instant multi-cm
# snap.

=== PER_LEG_TURN_OFFSET ===
            # Per-leg effective forward speed = commanded translation + a per-side steering offset
            # (+ for left legs, - for right, via LEG_LR). Feeding this into foot_target_for_leg
            # instead of the shared target_vx[0] means turning isn't a separate offset bolted on
            # after the fact - it's the same stride-amplitude/direction machinery walking already
            # uses, just driven per side. That's what lets stance legs actively sweep during a pure
            # in-place rotation (target_vx==0, target_turn!=0), and lets translate+turn compose for
            # free.
            # Stronger gain for pure in-place turning (target_vx ~0) than for turning while also
            # walking - see TURN_VX_GAIN_PURE's comment above for the evidence.

=== THETA_FF_DIRECTION_FIX ===
        # ported fix: feedforward nose-up bias timed to the currently-swinging pair's phase - see
        # FEEDFORWARD_PITCH_BIAS_RAD's comment above for the reasoning. active_pair/t only mean
        # anything while is_actively_moving (same condition that sets last_status["active_pair"] and t
        # above), so theta_ff stays 0 otherwise - no feedforward while idle/released, matching how
        # CORRECTION_FRACTION/PITCH_RATE_DAMPING also switch to their idle gains in that case.
        # Also gate this out during pure rotation (target_vx ~0, only turning). This bias's shape (a
        # half-sine nose-up push peaking mid-swing) came from trot_demo.py's FORWARD-walking dip -
        # support narrowing to 2 diagonal legs while forward momentum keeps carrying the body, a
        # fore-aft thing. Digging into the "still stalls like crazy" report, even after raising
        # TURN_VX_GAIN_PURE to this file's documented-safe ceiling (0.5*MAX_VX), turned up something
        # gain alone can't explain: the stalls line up with real physical stumbles, not just no-motion -
        # one stretch showed pitch surging +1.8 -> +7.5deg and body_xyz.x sliding ~0.06m within a
        # handful of samples, with yaw briefly reversing (-176.1 -> -173.7deg) before resuming - a real
        # destabilization, not friction stiction. Pure in-place rotation has no forward momentum to make
        # that same fore-aft dip - it's a torsional disturbance instead - so a bias shaped for the other
        # kind of disturbance is at best useless here and at worst an untested extra pitch push on an
        # already turn-disturbed gait at exactly the wrong moment. Same rule as yaw_hold above: don't
        # use a mechanism outside the context it was actually validated in.
        # Real fall, not a hypothesis: a straight backward walk (vx_target=-0.170, turn_target=0 the
        # whole time - not a turning problem) fell to a growing, one-directional pitch runaway: -5.4 ->
        # +5.8 -> +13.3 -> +23.6 -> +22.3deg -> abort at +25.3deg. Pitch trended positive (nose up) the
        # whole time, the opposite sign from the forward-walking dip (always nose-down) that
        # FEEDFORWARD_PITCH_BIAS_RAD's formula below was validated against in trot_demo.py. The formula
        # as ported (`-PITCH_SIGN * BIAS * sin(...)`) is always <=0 no matter which way you're walking -
        # it doesn't know that backward walking should, by the same physics that makes forward walking
        # dip nose-down, produce a mirrored nose-up dip instead (which matches what this fall's data
        # shows). So every swing during that backward walk got an always-negative feedforward push while
        # the real disturbance needing correction was nose-up - fighting the wrong direction every
        # half-cycle, on top of whatever theta_p/theta_d were doing. Fixed by mirroring the bias off
        # travel direction the same way foot_target_for_leg's own `direction` variable already does (+1
        # for vx>=0, -1 for vx<0) - forward walking is unaffected (direction=+1 reproduces the original
        # bias exactly), backward walking now gets the sign-flipped version instead of blindly reusing
        # forward's.

=== ROLL_TERM_MIRROR_FIX ===
            # Note: roll_term used to be added identically to every leg here, no per-side sign flip.
            # abad_geo's own sign is already mirrored left/right (via leg_ik_3d's oy term), so adding
            # the same delta to all four legs doesn't flare/narrow both sides symmetrically - it shoves
            # every foot's lateral position the same physical direction, widening stance on one side and
            # narrowing the other. Fine as small noise for standing/walking, but turning induces real
            # roll from the asymmetric left/right stance forces, and this term reacting to that roll
            # could progressively pull one side's feet inward right when the diagonal-trot support base
            # is already thin - a plausible cause of "legs come too close together" after turning. If
            # disabling it above (ROLL_ABAD_FRACTION = 0.0) stops the turn-then-fall, the fix is to
            # mirror the sign per leg (`abad = abad_geo + OY[leg] * roll_term`) instead of re-enabling
            # this as-is.
            # Fix applied: a run with turn_target=0 the entire time (straight-line forward walking, no
            # turning at all) showed exactly the failure predicted above - "robot going backwards during
            # forward walking" plus brief lift-ups close to losing balance. In the log, every
            # instantaneous backward jolt (body x decreasing between samples, e.g. 0.190->0.184,
            # 0.259->0.225) lines up with a roll_term spike (+0.92deg, -1.06deg) at that same sample, and
            # the worst body-z "lift" (0.365 vs the ~0.33-0.35 walking baseline) follows the biggest
            # roll_term spike (-1.17deg) one sample later. So it's not just turning-induced - the trot's
            # own side-to-side sway, even walking dead straight, was enough to trigger it. Applying the
            # mirrored fix: OY[leg] flips sign left/right (matching how abad_geo's own geometry is
            # already mirrored via leg_ik_3d's oy argument), so a positive roll correction now pushes the
            # two sides' ABAD joints in opposite directions (actually countering roll) instead of
            # shoving all four the same way, which is the mechanism this note was worried about.
